# Task 4：思考题

## 1. Make 和简单的 build.sh 有什么区别？

### 1.依赖关系

- Make按照“目标：依赖”规则工作，如果某个文件“过期”了（即其依赖文件的修改时间晚于该文件），就会自动重新编译这部分
- build.sh这类shell脚本就没有依赖关系，只是从上而下逐行跑一遍命令而已，没有原生的“只编译过期文件”的功能

### 2.任务与目标

- Make支持多目标与伪目标（如`clean`、`install`），而且目标之间可以设置依赖，比如`install`之前会自动先检查程序有没有编译好，如果没有就先构建再安装
- build.sh就没有这种内置的任务机制，也不存在依赖，如果需要实现不同的功能或是构建各任务之间的先后顺序，只能手动写逻辑控制

### 3.并行编译

- Make可以用`-jN`开启并行编译，可以自行根据依赖关系找出可以同时进行的任务并同时跑，有前后依赖关系的任务则会自动等前面的做完再跑后面的
- build.sh没法自行判断哪些任务可以同时跑，哪些任务要等前面的做完再跑，要实现这种功能需要人工操作


## 2. CMake 是编译器吗？

执行 `cmake --build build` 时，最终是谁在编译 C 源文件？

### 1.CMake不是编译器

编译器是像gcc这样做词法语法分析，把.c原代码翻译成.o的，而CMake是构建文件生成器，它读取CmakeLists.txt，生成底层构建脚本（build 目录下生成 Makefile），本身不做编译

### 2.最终是gcc这类c编译器

`cmake --build build` 只是封装调用底层构建工具，cmake 自己不执行编译命令。camke调用进入build目录执行make，make再去调用gcc编译c源文件

## 3. 为什么不希望每次都重新编译所有 `.c` 文件？

大型项目的`.c`文件数以千计，全部重新编译耗费大量时间，很多源文件都没有修改，它们的目标文件依然有效，没必要重复计算，只需编译改动以及受依赖影响的文件即可，大大提升效率
